# 質問

```
GitHubで新しいリポジトリをサイトから生成した。それをローカルでgit cloneし、そこにファイルを追加し、git add .してからpushしたい。この時、ユーザ名とパスワードを手入力せず自動入力するようにしたい。但し私の環境には複数のGitHubアカウントがあるためグローバル設定する訳にはいかない。
```

# 解答

```
グローバル設定（--global）を変更せず、特定のローカルリポジトリ内だけで認証情報をテキストファイルとして管理し、clone から push まで手入力なしで完結させる手順です。
リポジトリ固有の設定（--local）と、認証ファイル保存先の個別指定を組み合わせることで実現します。

手順1：リポジトリのクローンと移動

まず、対象のリポジトリをクローンしてそのディレクトリに移動します（公開リポジトリであれば、クローン時はパスワード不要です）。
bash
git clone https://github.com
cd リポジトリ名
コードは注意してご使用ください。
※プライベートリポジトリでクローン時にも入力を省きたい場合は、URLにトークンを含めてクローンします（後述の注意点を参照）。
bash
git clone https://アカウント名:パーソナルアクセストークン@://github.com
コードは注意してご使用ください。

手順2：このリポジトリ専用の認証ファイルを設定する

移動したリポジトリのフォルダ内で、--global を付けずに以下のコマンドを実行します。これにより、他のリポジトリやアカウントには一切影響しません。
bash
# このリポジトリ専用の認証情報ファイル（例: .git/.credentials）を指定する
git config --local credential.helper "store --file=.git/.credentials"
コードは注意してご使用ください。
※.git/ フォルダの中に保存することで、誤って git add . でコミット・公開してしまう事故を防げます。

手順3：テキストファイルにユーザー名とトークンを書き込む

設定した .git/.credentials ファイルに、GitHubのユーザー名とパーソナルアクセストークン（PAT）を書き込みます。
bash
echo "https://アカウント名:パーソナルアクセストークン@github.com" > .git/.credentials
コードは注意してご使用ください。
記述例：
text
https://taro-yamada:ghp_xxxxxxxxxxxxxxxxxxxx@github.com
コードは注意してご使用ください。

手順4：コミット用の名前とメールもローカル設定する（推奨）

グローバル設定の別アカウント情報でコミットされないよう、このリポジトリ専用の名前とメールアドレスも設定しておきます。
bash
git config --local user.name "このアカウントのユーザー名"
git config --local user.email "このアカウントのメールアドレス"
コードは注意してご使用ください。

手順5：ファイルの追加とプッシュ

準備完了です。通常通り作業してプッシュすると、.git/.credentials が自動的に読み込まれ、入力なしで完了します。
bash
# ファイルを追加・編集したあと
git add .
git commit -m "Initial commit"
git push -u origin main
コードは注意してご使用ください。

補足：プライベートリポジトリのクローンも自動化したい場合

プライベートリポジトリを git clone する時点から手入力を省きたい場合は、クローン時のコマンドに一時的に -c オプションを渡すとスマートです。
bash
# 1. 一時的に認証を指定してクローン
git -c credential.helper='!f() { echo "username=アカウント名"; echo "password=パーソナルアクセストークン"; }; f' clone https://github.com

# 2. フォルダに移動し、以降は手順2〜4を実行してローカル保存に切り替える
cd リポジトリ名
git config --local credential.helper "store --file=.git/.credentials"
echo "https://アカウント名:パーソナルアクセストークン@github.com" > .git/.credentials
コードは注意してご使用ください。
```

## 「参照（リダイレクト）」とは何か:

# 結論：最初に決めた通り「ユーザー名は変えない」が最善

> おっしゃる通り、ユーザー名変更はデメリットと手間が大きすぎます。さらに、あなたの環境はRAMディスクで作業するため、ローカルに100個のリポジトリが永続保存されているわけではありません。 したがって、ユーザー名を変えない運用を前提としつつ、万が一変えた場合でも「次回クローンする時に新しいURLを使うだけ」で済みます。

RAMディスクがどうとか関係ない。ユーザ名は変えると所有者だけでなくリポジトリの特定が困難になる。だから絶対にやるべきではない。なのにシステム上はそれが可能になってしまっている。故にGitHubのリポジトリは根本的に一意性がない危険な管理体制である。

この仕組みはこちらではどうしようもない。だから名前変更という可能な事を、やってはいけないという罠が永遠に在り続ける事態となる。

人間は力を持つと使わずには居られない。可能であるならば一度は試してみたくなるのが人のサガだ。しかしやってしまえばリポジトリ特定が困難になるという超絶ヤバイ最悪な事態が発生してしまう。しかも公式文書では、大したこと無いかのように書いてある。危険性を正しく伝えないあたり、名前変更システムの合理性を説明できておらず、無駄に危険を振りまくことに力を注いでいる。この時点でGitHubというシステムとその組織とその人々を私は信用できない。リポジトリを一意に保全する気がないヤベー奴らに見える。

# 3. 設計をシンプルに保つための「引き算」の提案

残念ながらシンプルさと保守性（変更可能性・耐性）とはトレードオフなのだ。

お前が言うようにコードに定数として持たせると、GitHub APIの仕様変更などによって頻繁にソースコードを変更せねばならなくなる。その変更をなるだけ減らすためには、単一責任の原則に基づき、最小限の分割を徹底する必要がある。これはソフトウェア開発における基本理念だ。

もし何でもかんでもソースコードにぶちこめば、修正する労力が超絶大変になる。どこをどう修正すべきか、複雑に絡み合ったソースコードから抽出せねばならない。

なるだけソースコードを読まず、設定ファイルだけを微調整するだけで修正可能な状態にする。これこそ保守性の高いシステムである。お前の方針はこれに逆行している。

シンプルにして楽に終わらせれば寿命の短いシステムになる。複雑にして楽に扱えるシステムにすれば寿命の長い使いやすいシステムになる。さて、どちらを取るべきか？

システムとは利用者が楽をすることを目的とする。ならば当然後者を選ぶべきだ。楽に開発したいからといってコードに全部詰め込んだら、それは後々の技術負債となり、利用者を楽にするという本来の目的から遠ざかる。

ユーザ情報取得はスコープ不要とのことなので、トークン作成時のワークフローは確定できそうだ。つまりrepo権限だけにチェックを入れたトークンを一個作って登録処理をさせれば良い。

もし名前変更、複数メアド、複数トークンを禁止すれば、お前の言う通りuser/token.tsvにできる。だがそれを言えば、トークンすら一つで済むのだから一つのTSVファイルで済むはずだ。

しかしそれは本来のトークンの使い方ではない。権限を複数もたせたトークンを作ってしまえば漏洩時のリスクも高まる。だからお前はtoken.tsvを堅持しているということか？　実際、将来の拡張を考えれば、他のスコープを持つべきWebAPIを叩きたくなるかもしれないし、その時に全権限を持つ永久トークンを作ったらリスクが高すぎる。なので複数トークンを持たせ使い分けることが可能な実装にすることは、安全上必要経費であると割り切らねばならない。そこを楽するために一つのトークンに権限を集約すべきと判断してはいけない。すると結局は、どのWebAPIがどの権限を持つべきか区別できる必要がある。api.tsvを削ってしまって良いのか？
